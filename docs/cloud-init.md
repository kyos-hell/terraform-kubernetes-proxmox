## Overview

This project uses **cloud-init** to automatically bootstrap Ubuntu VMs created by Terraform/Proxmox. Cloud-init allows declarative configuration of VMs at first boot without manual intervention, including:

- Hostname and FQDN setup
- SSH key distribution and authorization
- Package updates
- User creation and sudoers configuration
- Custom script execution via `runcmd`
- File creation via `write_files`
- System service management

**Key Components:**
- `cloud-init/user_data.tpl` — Generic VM bootstrap template (for Kubernetes workers/master)
- `cloud-init/user_data_ansible.tpl` — Specialized template for the Ansible control node
- `cloud-init/meta_data.tpl` — Instance metadata (cloud-init spec)
- Templates are processed by Terraform with variable interpolation and injected into VMs via Proxmox snippets

## Cloud-Init Templates

### Template Selection

In the Terraform configuration (`proxmox_cloud_snippets.tf`), the appropriate cloud-init template is selected based on the VM's **role**:

```hcl
source_raw {
  data = templatefile(
    "${path.module}/cloud-init/${each.value.role == "ansible" ? "user_data_ansible.tpl" : "user_data.tpl"}",
    { ... }
  )
}
```

- **If role == "ansible"** → Uses `user_data_ansible.tpl`
- **Otherwise** → Uses `user_data.tpl` (Kubernetes nodes)

## Configuration for Generic VMs

### File: `cloud-init/user_data.tpl`

Used for all Kubernetes nodes (master, workers). Handles basic VM provisioning.

**Content:**

```yaml
#cloud-config
hostname: ${hostname}
fqdn: ${hostname}.${domain}
manage_etc_hosts: true
package_upgrade: true

users:
  - default
  - name: ubuntu
    sudo: ALL=(ALL) NOPASSWD:ALL
    ssh_authorized_keys:
      - "${ssh_pub}"

ssh_pwauth: true

runcmd:
  - [ sh, -c, 'mkdir -p /home/ubuntu/.ssh || true' ]
  - [ sh, -c, 'chown -R ubuntu:ubuntu /home/ubuntu/.ssh || true' ]
  - [ sh, -c, 'chmod 700 /home/ubuntu/.ssh || true' ]
  - [ sh, -c, 'chmod 600 /home/ubuntu/.ssh/authorized_keys || true' ]
  - [ sh, -c, 'chown -R ubuntu:ubuntu /home/ubuntu || true' ]
```

**Configuration Breakdown:**

| Key | Purpose | Value |
|-----|---------|-------|
| `hostname` | Local hostname (without domain) | VM name (e.g., `k8s-master-01`, `ansible-01`, etc.) |
| `fqdn` | Fully qualified domain name | `${hostname}.${domain}` |
| `manage_etc_hosts` | Auto-populate `/etc/hosts` | `true` |
| `package_upgrade` | Run `apt upgrade` at boot | `true` |
| `users` | User definitions | `default` + `ubuntu` user |
| `ssh_authorized_keys` | Inject public key for SSH | Generated by Terraform |
| `ssh_pwauth` | Allow password SSH auth | `true` (for non-Ansible nodes) |
| `runcmd` | Execute commands at boot | Fix `.ssh` ownership/perms |

**What It Does:**

1. Sets hostname and FQDN
2. Updates system packages
3. Creates/enables `ubuntu` user with passwordless `sudo`
4. Adds public SSH key to `authorized_keys`
5. Ensures `/home/ubuntu/.ssh` has correct permissions (defensive)

## Configuration for Ansible Control Node

### File: `cloud-init/user_data_ansible.tpl`

Specialized template for control node (e.g., `ansible-01`). Includes SSH private key provisioning and systemd service for SSH ownership fix.

**Content:**

```yaml
#cloud-config
hostname: ${hostname}
fqdn: ${hostname}.${domain}
manage_etc_hosts: true
package_upgrade: true

users:
  - default
  - name: ubuntu
    sudo: ALL=(ALL) NOPASSWD:ALL
    ssh_authorized_keys:
      - "${ssh_pub}"

ssh_pwauth: false

write_files:
  - path: /home/ubuntu/.ssh/id_ansible
    owner: root:root
    permissions: '0600'
    content: |
${ssh_priv}
  
  - path: /home/ubuntu/.ssh/config
    owner: root:root
    permissions: '0600'
    content: |
      Host *
        IdentityFile /home/ubuntu/.ssh/id_ansible
        IdentitiesOnly yes
        StrictHostKeyChecking ask

  - path: /usr/local/bin/fix-ssh-owner.sh
    owner: root:root
    permissions: '0755'
    content: |
      #!/bin/sh
      # Wait for ubuntu user to exist, then fix .ssh ownership and permissions.
      for i in $(seq 1 120); do
        id ubuntu >/dev/null 2>&1 && break || sleep 1
      done
      mkdir -p /home/ubuntu/.ssh || true
      chown -R ubuntu:ubuntu /home/ubuntu/.ssh || true
      chmod 700 /home/ubuntu/.ssh || true
      if [ -f /home/ubuntu/.ssh/id_ansible ]; then
        chmod 600 /home/ubuntu/.ssh/id_ansible || true
        chown ubuntu:ubuntu /home/ubuntu/.ssh/id_ansible || true
      fi
      # populate known_hosts defensively
      ssh-keyscan -H 192.168.1.11 >> /home/ubuntu/.ssh/known_hosts 2>/dev/null || true
      chown ubuntu:ubuntu /home/ubuntu/.ssh/known_hosts || true

  - path: /etc/systemd/system/fix-ssh-owner.service
    owner: root:root
    permissions: '0644'
    content: |
      [Unit]
      Description=Fix /home/ubuntu/.ssh ownership and permissions
      After=cloud-final.target network.target local-fs.target
      Wants=network-online.target

      [Service]
      Type=oneshot
      ExecStart=/usr/local/bin/fix-ssh-owner.sh
      RemainAfterExit=yes

      [Install]
      WantedBy=cloud-final.target

runcmd:
  - [ sh, -c, 'systemctl daemon-reload || true' ]
  - [ sh, -c, 'systemctl enable --now fix-ssh-owner.service || systemctl start fix-ssh-owner.service || true' ]
  - [ sh, -c, 'mkdir -p /home/ubuntu/.ssh || true' ]
  - [ sh, -c, 'chmod 700 /home/ubuntu/.ssh || true' ]
  - [ sh, -c, 'if [ -f /home/ubuntu/.ssh/id_ansible ]; then chmod 600 /home/ubuntu/.ssh/id_ansible || true; fi' ]
```

**Key Differences from Generic Template:**

| Feature | Generic | Ansible Node |
|---------|---------|--------------|
| `ssh_pwauth` | `true` | `false` (key-only) |
| Private key file | Not provisioned | `write_files` injects `/home/ubuntu/.ssh/id_ansible` |
| SSH config | None | Custom `~/.ssh/config` for Ansible use |
| Ownership fix | Basic `runcmd` | Dedicated systemd service `fix-ssh-owner.service` |
| Known hosts | Not populated | Service populates known_hosts for master |

**Special Features:**

1. **Private Key Injection**: The `${ssh_priv}` variable contains the Terraform-generated private key, pre-indented for YAML block scalar format
2. **SSH Config**: Adds `~/.ssh/config` to specify identity file and SSH options
3. **Systemd Service**: `fix-ssh-owner.service` runs as `Type=oneshot` after cloud-final to fix ownership issues that may occur during cloud-init
4. **Known Hosts Population**: Service pre-populates known_hosts for the master node (e.g., 192.168.1.11) to avoid SSH host key verification issues

## Metadata Configuration

### File: `cloud-init/meta_data.tpl`

Minimal metadata file required by cloud-init specification.

**Content:**

```plaintext
instance-id: ${instance_id}
# local-hostname removed from meta_data to avoid ambiguity; use hostname in user-data instead
```

**Details:**

- `instance-id`: Unique identifier per VM instance (generated by Terraform as a random UUID)
- `local-hostname` is intentionally omitted to avoid conflicts with the hostname/fqdn set in user-data
- This file is injected into the VM via Proxmox cloud-init interface (ide2 device)

## Template Variables

### Variables Passed to Cloud-Init Templates

In `proxmox_cloud_snippets.tf`, the following variables are interpolated into templates:

```hcl
templatefile(
  "${path.module}/cloud-init/${...}.tpl",
  {
    hostname = each.value.name,           # VM name, e.g., "k8s-master-01", "ansible-01"
    domain   = var.domain,                # Example: "k8s.local"
    ssh_pub  = chomp(tls_private_key.ansible.public_key_openssh),
    ssh_priv = each.value.role == "ansible" 
               ? format("%s%s", "      ", replace(
                   chomp(tls_private_key.ansible.private_key_openssh), 
                   "\n", "\n      ")) 
               : ""                       # Indented private key for Ansible node only
  }
)
```

**Variable Breakdown:**

| Variable | Description | Example |
|----------|-------------|---------|
| `${hostname}` | VM hostname (short name) | `ansible-01`, `k8s-master-01`, `k8s-worker-01`, etc. |
| `${domain}` | DNS domain | `k8s.local` (example, configurable) |
| `${ssh_pub}` | SSH public key for authorized_keys | (ed25519 key) |
| `${ssh_priv}` | SSH private key (indented for YAML) | (ed25519 private key) |
| `${instance_id}` | Unique UUID per VM | (random UUID) |

**Important:** The private key (`${ssh_priv}`) is **only** interpolated for the Ansible node (`role == "ansible"`), not for Kubernetes nodes.

## Terraform Integration

### How Cloud-Init is Injected

1. **Template Processing**: `proxmox_cloud_snippets.tf` uses `templatefile()` to process `.tpl` files with variable substitution
2. **Snippet Creation**: Processed templates are uploaded to Proxmox as "snippets" (cloud-init config files):
   - User-data snippet: `${vm_name}.${domain}-ci-user.yml`
   - Metadata snippet: `${vm_name}.${domain}-ci-meta_data.yml`
3. **VM Injection**: In the VM module (`modules/proxmox_vm/main.tf`), the snippets are referenced:
   ```hcl
   initialization {
     datastore_id      = "local"
     interface         = "ide2"
     user_data_file_id = var.cloud_user_file_id
     meta_data_file_id = var.cloud_meta_file_id
     ip_config {
       ipv4 { address = "${var.ip}/${var.network_prefix}"; gateway = var.gateway_ipv4 }
     }
   }
   ```
4. **Cloud-Init Execution**: On VM first boot, Proxmox presents the snippets as cloud-init data source; cloud-init processes and applies configuration

### Snippet File Management

- **Created by**: `proxmox_virtual_environment_file` resource in `proxmox_cloud_snippets.tf`
- **Storage**: Proxmox local snippet storage (datastore_id = "local")
- **Naming Convention**: `${vm_name}.${domain}-ci-user.yml` and `-ci-meta_data.yml`
- **Lifecycle**: Snippets are created per-VM and managed by Terraform state

## SSH Key Management

### Key Generation

SSH keys are generated by Terraform using the `tls_private_key` resource:

```hcl
resource "tls_private_key" "ansible" {
  algorithm = "ED25519"
}
```

- **Type**: ED25519 (modern, secure)
- **Usage**: Single keypair shared across all cluster nodes for Ansible access
- **Storage**: Local file (if `write_private_key_local = true`): `./secrets/ansible_cluster_id_ed25519`

### Public Key Distribution

The public key is distributed via cloud-init to **all VMs** in the `ssh_authorized_keys` field:

```yaml
users:
  - name: ubuntu
    ssh_authorized_keys:
      - "${ssh_pub}"
```

This allows SSH access from the Terraform controller or from the Ansible control node.

### Private Key Placement

**For Kubernetes Nodes:** Private key is **NOT** included in cloud-init; nodes receive only the public key.

**For Ansible Node:** Private key is provisioned in `/home/ubuntu/.ssh/id_ansible` via cloud-init `write_files`:

```yaml
write_files:
  - path: /home/ubuntu/.ssh/id_ansible
    owner: root:root
    permissions: '0600'
    content: |
${ssh_priv}
```

The systemd service `fix-ssh-owner.service` later corrects ownership from `root:root` to `ubuntu:ubuntu` to avoid SSH permission issues.

### Security Considerations

- ✅ Private keys are not exposed in Terraform state (stored in secrets directory with `.gitignore`)
- ✅ Cloud-init injects keys only at first boot
- ⚠️ Private key must be protected locally (file permissions 0600)
- ⚠️ Do not commit private keys to version control

## Troubleshooting

### Cloud-Init Logs

On any VM, check cloud-init execution:

```bash
# Full cloud-init log
sudo tail -f /var/log/cloud-init-output.log

# Cloud-init status
sudo cloud-init status --long

# Cloud-init module logs (detailed)
sudo cat /var/log/cloud-init.log | grep "error\|ERROR\|fail\|FAIL"
```

### Common Issues

#### 1. SSH Key Ownership Problems

**Symptom:** Permission denied when trying to SSH from Ansible node to workers.

**Root Cause:** Cloud-init writes files as root; ownership not corrected to `ubuntu` user.

**Fix Applied:** 
- `fix-ssh-owner.service` (on Ansible node) waits for `ubuntu` user existence and fixes ownership
- `runcmd` in generic template also ensures defensive permission fixes

**Manual Check:**
```bash
ssh -i ./secrets/ansible_cluster_id_ed25519 ubuntu@<IP> 'ls -la ~/.ssh/id_ansible'
# Should show: ubuntu ubuntu 0600
```

#### 2. cloud-init Not Completing

**Symptom:** Some cloud-init tasks not executed; `runcmd` not fully applied.

**Root Cause:** VM not fully initialized when Ansible tries to connect.

**Fix Applied:** 
- `reboot_and_wait.sh` script waits for `cloud-init status --wait` before returning
- Terraform depends_on ordering ensures cloud-init completion

**Manual Check:**
```bash
ssh -i <key> ubuntu@<IP> 'sudo cloud-init status --wait'
```

#### 3. Hostname Not Set

**Symptom:** VM hostname is still `ubuntu` or default.

**Root Cause:** cloud-init hostname module ran before network was ready.

**Fix:** The `manage_etc_hosts: true` directive handles `/etc/hosts` population. Verify:
```bash
hostname -f
cat /etc/hostname
```

#### 4. package_upgrade Timeout

**Symptom:** First boot is very slow; apt locks conflict with cloud-init.

**Root Cause:** `package_upgrade: true` runs `apt update && apt upgrade` which can take minutes.

**Fix:** 
- Increase provisioner timeouts in Terraform
- Consider disabling package_upgrade in templates if using pre-updated base images

#### 5. Proxmox Snippet Not Found

**Symptom:** VM fails to boot or boots without cloud-init applied; error about missing snippet.

**Root Cause:** 
- Snippet file not created by Terraform
- Wrong datastore_id in snippet resource
- Network connectivity issue during snippet upload
- Wrond indente in .tpl

**Fix:**
```bash
# Verify snippets exist on Proxmox
ls -la /var/lib/vz/snippets/

# Check Terraform state
terraform state show proxmox_virtual_environment_file.cloud_user_config
```

## Best Practices

### 1. Template Maintainability

- Keep templates simple and readable; move complex logic to scripts
- Document variables at the top of each template
- Use version control (git) to track template changes
- Test template changes locally before deploying

### 2. Idempotence

- Use `creates:` guards in shell tasks to avoid re-execution
- Prefer `ansible.builtin.*` modules over raw shell commands where possible (for Ansible)
- Design cloud-init directives to be safe if run multiple times

### 3. Security

- Never commit private SSH keys to version control
- Use `.gitignore` for `./secrets/` directory
- Consider Vault or secrets manager for production environments
- Rotate SSH keys periodically
- Review cloud-init logs for any credential exposure

### 4. Customization

To customize cloud-init configuration:

1. **Modify Templates**: Edit `cloud-init/user_data.tpl` or `user_data_ansible.tpl`
2. **Add New Packages**: Extend `runcmd` or use `packages:` directive
3. **Custom Scripts**: Use `write_files:` to create files, then execute via `runcmd`
4. **User Creation**: Define additional users in `users:` section

Example: Add custom package to all nodes:

```yaml
# In cloud-init/user_data.tpl, add:
packages:
  - vim
  - curl
  - htop
```

### 5. Testing

Before running full deployment:

```bash
# Validate cloud-init syntax
cloud-init dryrun

# Test on a single VM first
terraform apply -target=module.vm["ansible-01"]

# Verify cloud-init ran
ssh ubuntu@<IP> sudo cloud-init status
```

### 6. Monitoring

After deployment, monitor cloud-init completion:

```bash
# Check all VMs for cloud-init done
for ip in 192.168.1.{10..14}; do
  echo "=== $ip ===" 
  ssh -i ./secrets/ansible_cluster_id_ed25519 ubuntu@$ip sudo cloud-init status
done
```

## Integration with Terraform Workflow

### Full Deployment Flow

1. **Terraform Plan**
   ```bash
   terraform plan -out=tfplan
   ```
   - Validates cloud-init templates
   - Shows snippet resources to be created

2. **Terraform Apply**
   ```bash
   terraform apply tfplan
   ```
   - Generates SSH keypair
   - Creates cloud-init snippet files
   - Uploads snippets to Proxmox
   - Creates VMs with snippet references
   - Injects cloud-init at first boot

3. **Cloud-Init Execution** (Automatic on VM first boot)
   - Proxmox presents snippets as cloud-init datasource
   - cloud-init processes user-data and meta-data
   - Applies hostname, packages, users, SSH keys
   - Executes runcmd tasks
   - Logs results to `/var/log/cloud-init-output.log`

4. **Post-Deployment Validation**
   ```bash
   # Check cloud-init completion
   terraform output vms
   ssh -i ./secrets/ansible_cluster_id_ed25519 ubuntu@<IP> sudo cloud-init status --long
   ```
