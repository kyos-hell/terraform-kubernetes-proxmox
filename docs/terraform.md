## Overview

This project uses **Terraform 1.0+** to automate the provisioning of a Kubernetes cluster on Proxmox VE. The infrastructure consists of:

- **5 VMs**: 1 Ansible control node, 1 Kubernetes master, 3 Kubernetes workers
- **Cloud-init**: Used for initial VM setup (network, SSH keys, packages)
- **Ansible**: Post-deployment configuration and Kubernetes cluster initialization
- **SSH Keys**: Generated by Terraform and distributed to all nodes
- **State**: Local state file (`terraform.tfstate`) stored in the repository root

### Architecture Flow

1. **Terraform** creates VMs on Proxmox with cloud-init configuration
2. **Cloud-init** initializes networking, installs packages, configures SSH keys
3. **Ansible** is installed and run to configure Kubernetes
4. **Kubernetes** is initialized via kubeadm and workers join the cluster

## Providers

### Configured Providers

**providers.tf** configures four providers:

| Provider | Version | Purpose |
|----------|---------|---------|
| `bpg/proxmox` | 0.42.0 | Proxmox VE infrastructure |
| `hashicorp/tls` | ~> 4.0 | Generate SSH keys (ED25519) |
| `hashicorp/local` | ~> 2.0 | Write files locally (SSH keys) |
| `hashicorp/random` | ~> 3.4 | Generate random values for uniqueness |

### Provider Configuration

#### Proxmox Provider

```hcl
provider "proxmox" {
  endpoint  = var.proxmox_endpoint  # https://192.168.1.100:8006/
  api_token = var.api_token         # user@realm!tokenid=secret
  insecure  = true                  # Accept self-signed certificates

  ssh {
    agent    = true                 # Use SSH agent for connections
    username = "root"               # Root user for Proxmox operations
  }
}
```

**Key Points:**
- `endpoint`: Proxmox VE API URL (typically `https://<proxmox-ip>:8006/`)
- `api_token`: Credentials (format: `user@realm!tokenid=secret`)
- `insecure = true`: Required for self-signed certificates (production: use proper certs)
- `ssh.agent`: Uses SSH agent for authentication to Proxmox

#### TLS Provider

Generates ED25519 SSH keys:

```hcl
resource "tls_private_key" "ansible" {
  algorithm = "ED25519"
}
```

## Key Resources

### 1. SSH Key Generation

```hcl
resource "tls_private_key" "ansible" {
  algorithm = "ED25519"
}
```

**Purpose:** Generate ED25519 SSH key pair for VM authentication
**Output:** `tls_private_key.ansible.private_key_openssh` and `.public_key_openssh`
**Used by:** Cloud-init user data to configure SSH access

### 2. Cloud-init File Upload (User Data)

```hcl
resource "proxmox_virtual_environment_file" "cloud_user_config" {
  for_each = local.vms_map

  content_type = "snippet"
  datastore_id = "local"
  node_name    = var.target_node
  file_name    = "cloud-init-user-${each.key}.yml"

  content = templatefile(
    "${path.module}/cloud-init/user_data.tpl",
    {
      vm_user        = var.vm_user
      ssh_public_key = tls_private_key.ansible.public_key_openssh
      # ... other variables
    }
  )
}
```

**Purpose:** Upload cloud-init user data template to Proxmox
**File Type:** Snippet (YAML template)
**Datastore:** `local` (Proxmox local storage)
**Content:** Templated user_data.tpl with SSH key injection

### 3. Cloud-init File Upload (Metadata)

```hcl
resource "proxmox_virtual_environment_file" "cloud_meta_config" {
  for_each = local.vms_map

  content_type = "snippet"
  datastore_id = "local"
  node_name    = var.target_node
  file_name    = "cloud-init-meta-${each.key}.yml"

  content = templatefile(
    "${path.module}/cloud-init/meta_data.tpl",
    {
      hostname = each.value.name
      # ... other variables
    }
  )
}
```

**Purpose:** Upload cloud-init metadata to Proxmox
**Content:** VM hostname and other metadata

### 4. VM Module Instantiation

```hcl
module "vm" {
  source   = "./modules/proxmox_vm"
  for_each = local.vms_map

  name               = each.value.name
  fqdn               = "${each.value.name}.${var.domain}"
  ip                 = each.value.ip
  cpu                = each.value.cpu
  memory             = each.value.memory
  role               = each.value.role
  template_vm        = data.proxmox_virtual_environment_vms.template.vms[0].vm_id
  node_name          = var.target_node
  network_bridge     = var.network_bridge
  system_disk        = var.system_disk
  cloud_user_file_id = proxmox_virtual_environment_file.cloud_user_config[each.key].id
  cloud_meta_file_id = proxmox_virtual_environment_file.cloud_meta_config[each.key].id
  network_prefix     = var.network_prefix
  gateway_ipv4       = var.gateway_ipv4
  tags               = var.vm_tags
}
```

**Purpose:** Create 5 VMs from a template loop
**Pattern:** `for_each` loop over `vms` variable
**Key Inputs:**
  - Template VM ID (from data source)
  - Cloud-init files (from proxmox_virtual_environment_file resources)
  - Network configuration (IP, gateway, prefix)
  - VM specs (CPU, memory)

- VM cloning from template
- Network configuration (IP, FQDN, gateway)

| `cpu` | number | Yes | Number of CPU cores |

### Module Outputs

**modules/proxmox_vm/outputs.tf:**

| Output | Type | Description |
|--------|------|-------------|
| `vm_id` | number | Proxmox VM ID |
| `ip` | string | VM IPv4 address |
| `fqdn` | string | VM fully qualified domain name |

### Module Resource: VM

**modules/proxmox_vm/main.tf** creates a `proxmox_virtual_environment_vm` resource:

```hcl
resource "proxmox_virtual_environment_vm" "vm" {
  name      = var.name
  node_name = var.node_name
  vm_id     = random_uuid.vm_id.keepers.id  # Deterministic ID

  clone {
    vm_id = var.template_vm
  }

  cpu {
    cores = var.cpu
  }

  memory {
    dedicated = var.memory
  }

  network_device {
    bridge = var.network_bridge
  }

  # Cloud-init IDE device (IDE2)
  ide {
    ide2 {
      cloudinit {
        user_data_file_id   = var.cloud_user_file_id
        metadata_file_id    = var.cloud_meta_file_id
      }
    }
  }

  # Tags for organization
  tags = var.tags

  lifecycle {
    ignore_changes = [
      started,  # Ignore manual start/stop outside Terraform
    ]
  }
}
```

**Key Points:**
- Clones from a template VM (avoiding full image copies)
- Uses `random_uuid` for deterministic VM ID generation
- Attaches cloud-init via IDE2 device (standard Proxmox integration)
- Allows manual start/stop outside Terraform

## Cloud-init Integration

### Cloud-init Files

The project uses three cloud-init templates:

#### 1. user_data.tpl (User Data)

Called by Terraform's `templatefile()` function to customize:
- SSH public key injection
- Package installation
- System configuration
- User creation

```hcl
content = templatefile(
  "${path.module}/cloud-init/user_data.tpl",
  {
    vm_user        = var.vm_user
    ssh_public_key = tls_private_key.ansible.public_key_openssh
  }
)
```

**Template Variables:**
- `${vm_user}`: Username created by cloud-init
- `${ssh_public_key}`: ED25519 public key from Terraform
- `${fqdn}`: VM fully qualified domain name
- Others as defined in cloud-init.md

#### 2. meta_data.tpl (Metadata)

Provides hostname and other metadata to cloud-init:

```hcl
content = templatefile(
  "${path.module}/cloud-init/meta_data.tpl",
  {
    hostname = each.value.name
  }
)
```

#### 3. Proxmox Integration

Cloud-init files are uploaded to Proxmox as snippets:

```hcl
resource "proxmox_virtual_environment_file" "cloud_user_config" {
  content_type = "snippet"
  datastore_id = "local"
  node_name    = var.target_node
  file_name    = "cloud-init-user-${each.key}.yml"
  content      = templatefile(...)
}
```

**How Proxmox Uses It:**
1. File is uploaded to Proxmox datastore as a snippet
2. VM's IDE2 device is configured with `cloudinit` block
3. Proxmox injects the snippet into the VM via cloud-init
4. On VM first boot, cloud-init processes the user data and metadata

## SSH Key Management

### Key Generation

```hcl
resource "tls_private_key" "ansible" {
  algorithm = "ED25519"
}
```

**Specifications:**
- Algorithm: ED25519 (modern, efficient, 256-bit)
- Format: OpenSSH format
- Lifetime: Persists across Terraform runs via state file

### Key Distribution

The public key is injected into all VMs via cloud-init:

```hcl
ssh_public_key = tls_private_key.ansible.public_key_openssh
```

Cloud-init template (`user_data.tpl`) adds it to `~ubuntu/.ssh/authorized_keys`

### Local Key Storage (Optional)

```hcl
resource "local_file" "ansible_private_key" {
  count           = var.write_private_key_local ? 1 : 0
  content         = tls_private_key.ansible.private_key_openssh
  filename        = "${path.module}/secrets/ansible_cluster_id_ed25519"
  file_permission = "0600"
}
```

**Purpose:** Write private key to local filesystem for SSH/Ansible access
**Location:** `./secrets/ansible_cluster_id_ed25519` (gitignored)
**Permissions:** 0600 (readable only by owner)
**Usage:** 
- Ansible playbook execution
- Manual SSH access to VMs
- Scripts (wait_for_ssh.sh, reboot_and_wait.sh)

## Deployment Workflow

### Step 1: Initialize Terraform

```bash
terraform init
```

**Actions:**
- Downloads providers (Proxmox, TLS, Local, Random)
- Creates `.terraform/` directory
- Initializes local state backend

### Step 2: Create terraform.tfvars

```bash
cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars with your cluster values
```

**Content:**
```hcl
proxmox_endpoint = "https://192.168.1.100:8006/"
api_token        = "user@realm!tokenid=secret"
target_node      = "pve-node-01"
domain           = "k8s.local"
# ... other variables
```

**⚠️ SECURITY:** Do NOT commit `terraform.tfvars` to Git (contains API token)

### Step 3: Validate Configuration

```bash
terraform validate
```

**Checks:**
- Syntax validation
- Variable type matching
- Provider requirements

### Step 4: Plan Deployment

```bash
terraform plan -out=tfplan
```

**Actions:**
- Queries Proxmox for template VM
- Calculates resource creation/updates
- Shows plan (resources to create, modify, delete)
- Saves plan to `tfplan` file

**Output Example:**
```
Terraform will perform the following actions:

  # module.vm["ansible-01"].proxmox_virtual_environment_vm.vm will be created
  + resource "proxmox_virtual_environment_vm" "vm" {
      + memory = 2048
      + name   = "ansible-01"
      + ...
    }

Plan: 11 to add, 0 to change, 0 to destroy.
```

### Step 5: Apply Configuration

```bash
terraform apply tfplan
```

**Actions:**
- Creates SSH key pair (tls_private_key)
- Uploads cloud-init files to Proxmox (proxmox_virtual_environment_file)
- Creates 5 VMs from template (proxmox_virtual_environment_vm)
- Writes private key locally (if enabled)
- Outputs VM information

**Typical Duration:** 5-15 minutes (VMs boot, cloud-init runs)

### Step 6: Verify Deployment

```bash
# Check outputs
terraform output vms

# SSH to Ansible node
ssh -i ./secrets/ansible_cluster_id_ed25519 ubuntu@192.168.1.10

# Verify cloud-init completion
cloud-init status --wait
```

## State Management

### State File Locations

| File | Purpose |
|------|---------|
| `terraform.tfstate` | Current state (production state) |
| `terraform.tfstate.backup` | Previous state backup |

The project uses Terraform's default local backend:

```hcl

```

**For Production:** Consider using remote backends:
- Terraform Cloud/Enterprise
- S3 + DynamoDB
- Consul
- Encrypted file storage

## Troubleshooting

### Issue: Template VM Not Found

**Error:**
```
Error: Unable to retrieve VMs
  on data.tf line 1: data "proxmox_virtual_environment_vms" "template":
  No VM matching tags ["template", "test"] was found
```

**Solution:**
1. Verify VM template exists in Proxmox
2. Check template has both tags: `template` and the value of `var.template_tag`
3. Verify template is on the correct node: `var.target_node`
4. List templates: `terraform console` → `data.proxmox_virtual_environment_vms.template.vms`

### Issue: API Token Invalid

**Error:**
```
Error: Unauthorized
  on providers.tf: provider "proxmox":
  API returned 401 Unauthorized (HTTP 401)
```

**Solution:**
1. Verify `api_token` format: `user@realm!tokenid=secret`
2. Check token is not expired (regenerate in Proxmox Web UI)
3. Check token has sufficient permissions (VMs, snapshots, files)
4. Verify endpoint URL is correct and accessible

### Issue: Insufficient Storage

**Error:**
```
Error: insufficient disk space
  on modules/proxmox_vm/main.tf line X:
  unable to create virtual disk
```

**Solution:**
1. Check Proxmox storage pool has enough free space: 5 VMs × 50GB each = 250GB minimum
2. Clean up old snapshots or unused VMs
3. Add additional storage to Proxmox
4. Reduce `system_disk.size` in variables

### Issue: Network Bridge Not Found

**Error:**
```
Error: Bridge vmbr0 not found
  on modules/proxmox_vm/main.tf line X
```

**Solution:**
1. Verify bridge name in Proxmox: `ip link show` on Proxmox host
2. Check `var.network_bridge` matches actual bridge name
3. Ensure bridge has IP configuration if using static IPs
4. Update terraform.tfvars with correct bridge name

### Issue: VM Not Receiving IP Address

**Error:** VM shows in Proxmox but no IP assigned

**Solution:**
1. Verify cloud-init ran: `cloud-init status --wait` on VM
2. Check user_data template contains network config
3. Verify gateway_ipv4 matches actual network gateway
4. Check network subnet (network_prefix) is correct

### Issue: SSH Connection Refused

**Error:**
```
ssh: connect to host 192.168.1.11 port 22 not open
```

**Solution:**
1. Wait for cloud-init to complete: `cloud-init status --wait`
2. Verify VM is running in Proxmox Web UI
3. Check SSH is enabled in cloud-init template
4. Verify firewall rules on VM
5. Check SSH key permissions: `chmod 0600 ./secrets/ansible_cluster_id_ed25519`

### Issue: State File Corruption

**Error:**
```
Error reading state file: invalid JSON
```

**Solution:**
1. Restore from backup: `cp terraform.tfstate.backup terraform.tfstate`
2. Re-run plan: `terraform plan`
3. If manual intervention needed, edit `terraform.tfstate` carefully (valid JSON only)
4. Consider switching to remote backend for better protection

## Best Practices

### 1. State Management

**✅ DO:**
- Keep state file backed up
- Use remote backends for production
- Restrict state file access (permissions 0600)
- Store state in version control (with encryption for remote backends)

**❌ DON'T:**
- Commit state file with sensitive data to public Git repos
- Manually edit state file
- Share state file via email or chat

### 2. Variable Management

**✅ DO:**
- Use `terraform.tfvars` for environment-specific values
- Mark sensitive variables (api_token, vm_user) as `sensitive = true`
- Use `.gitignore` to prevent committing sensitive files
- Document all variables in comments

**❌ DON'T:**
- Hardcode API tokens in Terraform files
- Commit `terraform.tfvars` to Git
- Store credentials in `.tf` files
- Log sensitive values

### 3. Deployment

**✅ DO:**
- Always run `terraform plan` before `terraform apply`
- Review plan output carefully
- Use `-out=tfplan` to save plan before applying
- Tag all resources for organization

**❌ DON'T:**
- Run `terraform apply` without reviewing plan
- Use `-auto-approve` in production
- Deploy changes without testing
- Modify resources outside Terraform

### 4. SSH Keys

**✅ DO:**
- Regenerate keys periodically (every 6-12 months)
- Store private keys in encrypted storage
- Use SSH agent for key management
- Set correct permissions (0600)

**❌ DON'T:**
- Commit private keys to Git
- Use weak algorithms (RSA 1024-bit)
- Log SSH keys in debug output
- Share keys across multiple environments

### 5. Cloud-init

**✅ DO:**
- Test cloud-init templates before deployment
- Use user-data sparingly (keep it simple)
- Log cloud-init output for debugging
- Wait for cloud-init to complete before running Ansible

**❌ DON'T:**
- Inject secrets directly in cloud-init templates
- Use heavy workloads in user-data (use Ansible instead)
- Rely on cloud-init for Kubernetes configuration
- Run cloud-init multiple times without idempotence

### 6. Variables

**✅ DO:**
- Define sensible defaults for all variables
- Use appropriate types (string, number, bool, object, list)
- Add validation rules for critical variables
- Document each variable's purpose

**❌ DON'T:**
- Create variables without defaults (unless truly required)
- Use generic names (var.x, var.temp, etc.)
- Mix concerns in a single variable
- Skip validation for IP addresses or other structured data

### 7. Modules

**✅ DO:**
- Keep modules focused and reusable
- Output all necessary information from modules
- Version modules for production use
- Test modules in isolation

**❌ DON'T:**
- Create overly complex modules
- Hide dependencies inside modules
- Hardcode values in module code
- Create circular dependencies between modules

## Security Considerations

### 1. API Token Rotation

The Proxmox API token should be rotated every 3-6 months:

1. Generate new token in Proxmox Web UI
2. Update `terraform.tfvars` with new token
3. Run `terraform plan` to verify (should show no changes)
4. Delete old token in Proxmox Web UI

### 2. SSH Key Rotation

SSH keys should be rotated every 6-12 months:

1. Delete old SSH key from VMs' authorized_keys
2. Destroy VMs: `terraform destroy`
3. Update cloud-init template if needed
4. Re-apply: `terraform apply` (generates new keys)

### 3. Network Security

**Restrict Proxmox API Access:**
- Use firewall rules to limit API access
- Use VPN for remote access
- Disable insecure HTTP (use HTTPS only)
- Use proper TLS certificates (not self-signed in production)

**Restrict SSH Access:**
- Use SSH key authentication only (no passwords)
- Restrict SSH to specific subnets if possible
- Use SSH agent for key management
- Monitor SSH access logs

### 4. Secrets in Logs

Be careful with debug logging:

```bash
# ❌ DON'T: This logs sensitive data
export TF_LOG=DEBUG
terraform plan > plan.log

# ✅ DO: Use filtering
terraform plan 2>&1 | grep -v "api_token"
```
